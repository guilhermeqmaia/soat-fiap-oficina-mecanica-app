# Evidencia — HPA sob carga real pelo API Gateway (12/09/2026)

Ambiente: conta AWS propria (ADR-0007), EKS `oficina-mecanica-eks` (2x `m7i-flex.large`),
app com 2–10 replicas (HPA CPU 70% / mem 80%, `requests.cpu=100m`), NLB interno,
API Gateway `https://u0lz10s1i4.execute-api.us-east-1.amazonaws.com`.
Gerador: k6 local (`perf/load.js`, JWT assinado com o segredo compartilhado).
Prometheus + Grafana instalados via `scripts/aws-observability.sh prometheus` (1m48).

## Execucao 1 — `VUS=60`, rampa de 30 s (abortada pelo SLO em ~21 s)

| Metrica | Valor |
|---|---|
| Requisicoes | 1.659 (41,5 rps) |
| Leitura p95 / avg / max | 165 ms / 151 ms / 1.162 ms |
| Falhas | 109 (6,6%) — respostas 429 do throttler da app |

O k6 abortou (`abortOnFail`) porque os thresholds de escrita/leitura contabilizam
os 429 como falha. Mesmo assim o HPA reagiu na rampa:

```
SuccessfulRescale  New size: 4; reason: cpu resource utilization (percentage of request) above target
SuccessfulRescale  New size: 6; reason: cpu resource utilization (percentage of request) above target
```

## Execucao 2 — `VUS=40`, 4 min + rampa, `--no-thresholds`

| Metrica | Valor |
|---|---|
| Requisicoes | 16.617 (54 rps) |
| Leitura p95 | **176 ms** (ponta a ponta: gateway → authorizer → VPC Link → NLB → pod) |
| 429 (throttler da app) | 4.684 (28%) |
| Replicas durante o teste | 6 (herdadas da execucao 1); scale-down para 4/5 apos o cooldown ("All metrics below target") |
| CPU dos pods | 4–9% do request — a carga foi absorvida com folga |

## Conclusoes

1. **HPA funciona no cluster gerenciado** (criterio da US-F3-05): escalou 2 → 4 → 6 por CPU e
   voltou apos o cooldown.
2. **Achado de arquitetura:** atras do VPC Link + NLB a app enxerga um unico IP de origem
   (ENI do VPC Link); o throttler por IP do monolito (100 req/60 s) vira um limite **global**.
   O rate limiting passa a ser exclusivo do gateway (400 rps / burst 800 — ADR-0005) e o
   overlay `k8s-aws` sobe a app com `THROTTLER_DISABLED=true` (a execucao 3, abaixo, confirma).
3. Latencia p95 de ~176 ms pelo gateway e consistente com os ~440 ms de uma chamada isolada
   (cold path do authorizer com cache de 300 s).

## Execucao 3 — apos `THROTTLER_DISABLED=true` no overlay (`VUS=60`, 3 min + rampa)

| Metrica | Valor |
|---|---|
| Requisicoes | 19.415 (78 rps) |
| Taxa de erro | **0,11%** |
| 429 (throttler da app) | **0** |
| Leitura p95 | 172 ms |
| Thresholds do k6 (SLO) | **OK** |
| HPA | partiu de 2 replicas e escalou **2 → 4 → 6 → 8** por CPU durante a carga |

```
SuccessfulRescale  New size: 4; reason: cpu resource utilization (percentage of request) above target
SuccessfulRescale  New size: 6; reason: cpu resource utilization (percentage of request) above target
SuccessfulRescale  New size: 8; reason: cpu resource utilization (percentage of request) above target
```

Com o rate limit apenas na borda, a app absorve ~80 rps pelo gateway dentro do SLO
e o autoescalonamento responde em < 1 min. O throttling do gateway (400 rps) nao foi
atingido neste volume.
